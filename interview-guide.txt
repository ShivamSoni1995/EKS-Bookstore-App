## 🏗️ Architecture Overview (Quick Glance)

```
Developer → GitHub → GitHub Actions Pipeline → Docker Hub → EKS Cluster → ALB → Users
                           ↓
                    Security Scans (4 tools)
                           ↓
                    Prometheus/Grafana Monitoring
```

**Components:**
- **Frontend**: React/Nginx UI (Port 80)
- **Backend**: Node.js API (Port 3000)
- **Infrastructure**: EKS cluster, 2 t3.medium nodes
- **Ingress**: AWS Application Load Balancer
- **Monitoring**: Prometheus + Grafana + Alertmanager

| **eksctl over Console** | Reproducible, version-controlled, faster setup | AWS Console, Terraform |

## ⚙️ IAM Roles & Permissions

| Role | Purpose | How It Works |
|------|---------|--------------|
| **eksClusterServiceRole** | EKS manages AWS resources | Allows EKS to create ELBs, security groups |
| **eksNodeGroupRole** | Worker nodes access AWS | Allows nodes to pull ECR images, join cluster |
| **ALB Controller Role** | Creates load balancers | OIDC-based, no long-term credentials |
| **github-actions-user** | CI/CD deploys to cluster | Limited to EKS describe/deploy only |

**Why OIDC over Access Keys?**
- No long-term credentials to manage
- Automatic token rotation
- Better audit trail
- More secure (time-limited tokens)

## 🚀 Auto-Scaling Strategy

### Horizontal Pod Autoscaler (HPA):
```
UI:  2-8 replicas  | Triggers: CPU >70% or Memory >80%
API: 2-10 replicas | Triggers: CPU >70% or Memory >80%
```

### Why These Numbers?
- **Min 2**: High availability (survive 1 pod failure)
- **Max 8/10**: Cost control + sufficient for traffic
- **70% CPU**: Headroom for traffic spikes
- **Scale-up**: 30 seconds
- **Scale-down**: 5 minutes (prevents flapping)

### Cluster Autoscaler:
```
Nodes: 2-4 t3.medium
Triggers: Pending pods for 60 seconds
Scale-down: After 10 min of <50% utilization
```

## 🎓 Challenges Faced & Solutions

### Challenge 1: ALB Controller Not Creating Load Balancer
**Problem**: Ingress stuck in pending state
**Root Cause**: Missing IAM OIDC provider
**Solution**: Created OIDC provider with `eksctl utils associate-iam-oidc-provider`
**Learning**: Always verify OIDC before installing AWS controllers

### Challenge 2: Pods Crashing (CrashLoopBackOff)
**Problem**: Pods restarting every 30 seconds
**Root Cause**: Health check path was incorrect
**Solution**: Fixed readiness probe from `/health` to `/`
**Learning**: Always test health endpoints before deployment

### Challenge 3: High ALB Costs
**Problem**: ALB costing $40/month vs expected $20
**Root Cause**: Multiple ALBs created per environment
**Solution**: Consolidated to single ALB with path-based routing
**Learning**: Use Ingress annotations wisely to share ALBs

### Challenge 4: Security Scan False Positives
**Problem**: Trivy blocking deployment for LOW severity issues
**Root Cause**: Too strict severity threshold
**Solution**: Changed from `CRITICAL,HIGH,MEDIUM` to `CRITICAL,HIGH`
**Learning**: Balance security with pragmatism, tune over time

### Challenge 5: Prometheus Storage Full
**Problem**: Prometheus pod evicted after 1 week
**Root Cause**: Default storage was 2Gi, retention 15 days
**Solution**: Increased to 10Gi with proper retention policy
**Learning**: Calculate storage needs: (samples/sec × retention days × 2 bytes)

## 🎤 Common Interview Questions & Answers

### Q: Why Kubernetes and not just EC2 with Docker?
**A**: "Kubernetes provides built-in features like auto-scaling, self-healing, rolling updates, and service discovery. With EC2, I'd have to build all this myself. For a production app, K8s abstracts complexity and provides battle-tested patterns. EKS gives me managed control plane so I focus on applications, not infrastructure."

### Q: How do you handle secrets in Kubernetes?
**A**: "I use Kubernetes Secrets for sensitive data, never commit to Git. In production, I'd use AWS Secrets Manager or HashiCorp Vault with External Secrets Operator. All secrets are encrypted at rest in etcd. For GitHub Actions, I use repository secrets with least-privilege access."

### Q: What happens if a pod crashes?
**A**: "Kubernetes automatically restarts it (self-healing). If it keeps crashing, I have alerts set up in Alertmanager that notify me via Slack within 2 minutes. I check pod logs with `kubectl logs`, describe the pod for events, and fix the root cause. Rolling updates ensure zero downtime during deployments."

### Q: How do you monitor the application?
**A**: "I use the Prometheus-Grafana stack. Prometheus scrapes metrics every 30 seconds from pods via ServiceMonitors. Grafana provides dashboards for CPU, memory, network, and custom application metrics. Alertmanager routes alerts to Slack for critical issues like pod crashes or high error rates. I track SLOs like 99.9% uptime and <500ms p95 latency."

### Q: Explain your CI/CD pipeline.
**A**: "Code push triggers GitHub Actions. First, security scanning - GitLeaks checks for secrets, SonarQube analyzes code quality, OWASP checks dependencies, and Trivy scans the Docker image. If all pass, Docker builds and pushes to Docker Hub. Then kubectl does a rolling update to EKS with health checks. The entire process takes 10-15 minutes with full automation and zero downtime. If any security scan fails, deployment is blocked."

### Q: How do you handle traffic spikes?
**A**: "I configured Horizontal Pod Autoscaler to scale from 2 to 8 replicas based on CPU (70%) and memory (80%) thresholds. When traffic increases, HPA scales up pods within 30 seconds. ALB distributes traffic across all healthy pods. For nodes, Cluster Autoscaler adds more EC2 instances if pods are pending. I've tested this handling 3x normal traffic successfully."

### Q: What's your rollback strategy?
**A**: "Kubernetes rolling updates are set to maxUnavailable: 1 and maxSurge: 1, so it updates one pod at a time while maintaining availability. If health checks fail, the rollout automatically pauses. I can manually rollback with `kubectl rollout undo`. In the pipeline, if post-deployment tests fail, it triggers an automatic rollback to the previous image. I've tested this - rollback takes under 60 seconds."

### Q: How do you ensure security?
**A**: "Security is integrated at every stage: GitLeaks prevents secret leaks, SonarQube catches code vulnerabilities, OWASP finds vulnerable dependencies, and Trivy scans images. In runtime, I enforce Pod Security Standards (restricted mode), Network Policies for zero-trust networking, and RBAC for least-privilege access. All images are signed with Cosign. Critical vulnerabilities block deployments immediately."

### Q: What would you improve?
**A**: "I'd add: 1) Service mesh (Istio) for advanced traffic management and mTLS, 2) GitOps with ArgoCD for declarative deployments, 3) Multi-region setup for disaster recovery, 4) Advanced cost optimization with spot instances and Cluster Autoscaler, 5) Chaos engineering with Chaos Mesh to test resilience, 6) Integration with AWS Secrets Manager for production secrets."

## 🎯 Technical Deep Dives (If Asked)

### How Kubernetes Networking Works:
```
Request Flow:
1. User → ALB (Layer 7)
2. ALB → Ingress Controller
3. Ingress → Service (ClusterIP)
4. Service → Pods (via iptables rules)
5. Pod → Container (via CNI)

Key Concepts:
- CNI Plugin: AWS VPC CNI (assigns pod IPs from VPC)
- Service Types: ClusterIP (internal), LoadBalancer (external)
- kube-proxy: Maintains iptables rules for service routing
```

### How HPA Works:
```
1. Metrics Server collects pod CPU/memory every 15s
2. HPA controller queries Metrics API every 15s
3. If actual > target: Calculate needed replicas
4. Formula: ceil[currentReplicas × (currentMetric / targetMetric)]
5. Update deployment with new replica count
6. Wait 3 minutes before next scale-up (stabilization)
```

### How GitHub Actions Connects to EKS:
```
1. GitHub Actions runner starts
2. Configure AWS credentials (access key or OIDC)
3. aws eks update-kubeconfig --name cluster
4. Downloads cluster CA cert and creates ~/.kube/config
5. kubectl commands use this config
6. IAM authenticates via aws-iam-authenticator
7. EKS validates IAM role has permissions
```
